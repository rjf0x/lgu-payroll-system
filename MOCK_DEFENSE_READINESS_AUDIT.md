### Components and data flow

`routes/web.php` connects controllers, Form Requests, Eloquent models, services, and Blade views. There is no `routes/api.php` in this checkout and no API route registration in `bootstrap/app.php`. The original route inventory listed 138 non-vendor routes; follow-up payroll inclusion/removal/confirmation routes extend that baseline. Custom role/permission tables and Gate definitions implement RBAC; this is not Spatie Permission. There is no repository layer or policy directory required by this architecture.

The payroll path is:

```text
Employee + employment + compensation + configured assignments
  → monthly payroll period/run
  → compute eligible employment records
  → enter/confirm payable days and manual adjustments
  → submit → independent review/approve → finalize
  → transactional registry outbox
  → scheduled dispatch → blockchain queue → authenticated Node bridge
  → durable SQLite signing journal → Web3Signer → Besu contract
  → authoritative on-chain read + current payroll hash comparison
```

Payroll computation happens **inside Laravel**, not in an external Excel-import workflow. `PayrollComputationService::basicPay()` uses monthly rate × service fraction × `min(1, payable_days / 22)`, or daily rate × payable days (`app/Services/PayrollComputationService.php:278`). It calculates configured contributions and an annualized withholding projection divided by twelve (`:204`, `:240`). These are implemented formulas, not a finding that LGU payroll policy or current statutory law has been professionally approved.

There is no payroll-register upload/import/reconciliation endpoint. `PayrollRegisterController::export()` and `PayrollSpreadsheetService::generate()` produce XLSX output. README references to “CSV registers” and CSV formula protection are stale relative to the current XLSX implementation (`README.md`, “Reports and background workers”; `app/Http/Controllers/PayrollRegisterController.php:24`). The audit does not treat an import module as required because the implemented computation path fulfills the stated alternative.

F05 adds `PayrollRegisterService` for non-editable runs, including PENDING_APPROVAL, APPROVED and FINALIZED. It builds columns from saved earnings, deductions and employer contributions, without querying current type configuration for labels or classification. The register's printable Blade view and XLSX use that same data; XLSX maps historical columns by position and stable keys rather than matching header names. Editable Draft/Returned/Rejected previews retain their existing configured-column workflow. Existing name snapshots already preserve original descriptions, so no new snapshot migration was necessary.

### Configuration and service dependencies

Required groups are application key/environment, database connection, session/cache/queue stores, Vite assets, and payroll reference data. `config/blockchain.php` separates legacy `BLOCKCHAIN_*`/`BESU_*` configuration from the versioned `PAYROLL_REGISTRY_*` configuration. The latter requires organization namespace, bridge URL/token, chain ID, genesis hash, contract address/runtime code hash, signer address, and deployment block. The bridge separately requires its matching `BESU_BRIDGE_*` settings and a persistent journal.

F04 adds `config/payroll.php`: each non-regular type requires a `PAYROLL_SUPPLEMENTAL_POLICY_REFERENCE` or `PAYROLL_ADJUSTMENT_POLICY_REFERENCE` and its corresponding `*_CALCULATION_METHOD`. These are unset by default. The only supported method, `existing_monthly`, is available only when MAO has explicitly confirmed that the existing calculations apply to that transaction type; other or missing treatments remain blocked. This is configuration, not a new policy-management screen or an automatic tax exemption. The outstanding decisions and operational boundary are recorded in `docs/payroll-approval-workflow.md`, “F04: compensation uniqueness and non-regular payroll.”

Current observations: `APP_ENV=local`, debug enabled, database queue selected, registry capture enabled, and the **legacy driver set to `simulated`**. These settings can coexist: registry submission uses `PayrollRegistryClient`, independently of the legacy driver binding. Existing registry-enabled finalized runs must be demonstrated through their registry record, not through the legacy Anchor action.

`routes/console.php:12` schedules registration dispatch each minute. The application needs an active scheduler, blockchain worker, bridge, signer, and validator quorum for asynchronous progress. An empty current backlog does not prove that the scheduler and worker are running. Report generation can optionally use the separate `reports` queue (`app/Http/Controllers/PayslipController.php:36`).

### MySQL/blockchain consistency

**Versioned path:** `PayrollApprovalService::finalize()` atomically writes FINALIZED, approval history, audit and the QUEUED registration. Capture/config/persistence errors roll back that transaction (`PayrollRegistrationTest.php:89`, `:103`). Network operations happen later, outside this financial transaction (`PayrollRegistrationService.php:88`).

The bridge journals its envelope and signed bytes **before broadcasting** (`RegistryBridge.mjs:89`). Retries replay identical bytes. SQLite durable storage and a single-writer lock protect nonce allocation (`RegistryStore.mjs:8`). Leases, due dates, request idempotency and reconciliation address duplicate workers and lost responses. Passing tests cover these failure modes and journal backup to temporary databases.

An accepted chain transaction followed by failed MySQL status persistence can leave the application pending temporarily. This is an expected reconciliation case; the durable bridge record and on-chain lookup support recovery. It is not claimed to be a distributed ACID transaction. If the bridge journal is lost, recovery and nonce management still require operator care; the actual restore drill was not run.

**Outage semantics:** Local payroll can correctly remain FINALIZED while registration is QUEUED/RECONCILING or even FAILED/CONFLICT. The application must keep these states visibly separate. Tests verify an outage does not claim MATCH and does not undo financial finalization (`PayrollRegistrationTest.php:155`; `PayrollVerificationTest.php:133`). A pending or unavailable proof is not successful anchoring.

**Legacy path risk:** `BlockchainAnchorService::anchor()` holds a MySQL transaction while `submitAnchor()` calls the external driver (`app/Services/BlockchainAnchorService.php:64`, `:89`). In legacy Besu mode, an accepted transaction followed by local persistence failure can create an on-chain/local-state gap without the versioned journal guarantees. Registry-backed runs block this path (`:75`). Also, the legacy digest omits several fields covered by registry v1 and uses delimiter-joined strings (`:30`). Do not use it as the preferred proof for new payrolls. Current legacy configuration is simulated and produces no independent chain evidence.

Its results distinguish MATCH, MISMATCH, PENDING, NOT_REGISTERED, UNAVAILABLE and INVALID_EVIDENCE. It compares current data, captured digest/payload, identity and on-chain digest (`:61`). An outage after a previous match records unavailable rather than reusing a previous conclusion. These are passing test results, not fresh live-chain verification results.

Private signing material is outside tracked application code, under ignored private development storage and signer mounts; the bridge uses remote signing. `.env` and private storage are excluded from tracked release material. No actual keys or passwords were printed or tested. Filesystem ACLs, key backup security and independently operated validators were not verified.
